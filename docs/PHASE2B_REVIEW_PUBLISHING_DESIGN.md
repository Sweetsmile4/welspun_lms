# Phase 2B review and publishing design

29 October 2026. Written before implementation after reading the requested baseline reports/designs, Phase 0 proposals and prototype/security audit and inspecting draft, authorization, audit, receipt and test source. This implements only synthetic internal backend workflow. No corporate approval hierarchy, named SME, production policy or industrial threshold is inferred.

## Development policy and evidence

Composition must explicitly supply a versioned development policy key and requiredApprovals (bounded 1–5 as an implementation limit, no default). Each submission captures that policy. Publication requires the same configured policy and all distinct assigned reviewers' approvals (assignment slots equal requiredApprovals). Real reviewer number, qualifications, capacities and independence require Welspun approval. A current course.review.decide grant and explicit assignment are the synthetic qualification, not caller claims or job titles. Qualification is rechecked on assignment, decision and publication, including actor/account, role/grant validity and authoritative scope. Revocation before publication invalidates readiness.

Author, submitter and any known contributor cannot be assigned or decide. Phase 2A lacks complete contributor history; add optional internal editedBy provenance, initialized on new drafts and accumulated on edits, bounded to 100. Absence denotes legacy unknown history: submission fails closed and edits must not fabricate completeness. No migration of old approvals/history. Author/publisher roles may overlap only with explicit publish permission and independent reviewer evidence; no production rule is implied.

## State machine

Draft/archived lifecycle remains separate. Readiness means a nonarchived, bounded valid draft with complete provenance, at least one module and at least one lesson in every module; no new persisted ready flag. Submission stores the exact snapshot. Review states: submitted → inReview (first assignment); inReview → approved when configured distinct approvals are complete; inReview → changesRequested or rejected; submitted/inReview/approved/changesRequested/rejected → superseded only when current content is stale; approved → published. Further edits never rewrite decisions. Changed/rejected work requires an edited revision and a new review; one submission per draft revision avoids ambiguous competing approval sets. Pending stale reviews can be explicitly superseded; publication/decision always checks current bytes/revision even without that transition.

Submit requires course.review.submit and exact current draft revision/digest. Assign requires course.review.assign plus qualified independent target. Decisions require course.review.decide, explicit assignment, exact review and draft revisions/digest, no previous decision for that reviewer; bounded structured feedback is required for changes/rejection. Supersede requires submit permission and stale evidence; it preserves all prior decisions. Publishing requires course.release.publish, approved state, current exact snapshot, all required evidence/current qualifications and expected previous release number. No security-admin bypass. Terminal invalid transitions conflict; archived drafts cannot be submitted/decided/published. Historical review/release reads remain possible with explicit read grants after archive.

## Canonical content and immutable snapshots

Canonical digest algorithm catalog-snapshot-v1: strict parsed Course + Draft, serialized Dates as UTC ISO strings, recursively lexically sorted object keys, preserved array order, SHA-256. Include stable IDs, organization/owner/scope, draft ID/revision/lifecycle, complete metadata, ordered modules/lessons/content/local revisions, all contributors and creation/update attribution/time. Thus both revision and bytes must match. No generic Date-to-empty-object hashing. Snapshot schema and digest algorithm versions are stored. No normalization of text/Unicode beyond existing validated contracts; byte changes require new approval.

ReviewRequest stores immutable submission/snapshot/binding/policy/actor/time plus a revision-controlled workflow projection (status, reviewers and evidence IDs). ReviewEvidence is append-only assignment/approve/changesRequested/reject/supersede attribution, exact binding/digest, structured feedback and time. Evidence rows are never rewritten. CourseRelease is append-only: unique ID, organization/course, monotonic number, exact source draft/revision/digest/algorithm, complete self-contained snapshot, scope, policy and approval-evidence snapshots/IDs, publisher/time and lifecycle=published. No mutable current-release pointer, withdrawal, automatic supersession or release editing is implemented. New corrections require a fresh revision/review/release. Embedded lesson snapshots intentionally avoid a separate lesson-release graph until reuse is required; immutable module/lesson IDs/order/content remain self-contained.

## Authorization, atomicity and replay

Add course.review.submit/read/assign/decide and course.release.publish/read. Resolve current stored course ownership/scope through the existing resolver; own scope only supports submit/read, not reviewer/publisher authority. Publisher readiness and release reads never depend on caller-provided scope. All operations use the same trusted actor and organization write fence. Repository CAS guards review revisions; unique indexes guard review identity, reviewer decisions, release numbers and source revision publication. Histories authorize the course before cursor/limit queries; no unbounded global listing or counts.

New receipt operations course.review.command.v1 and course.release.publish.v1 use new strict small acknowledgements. Existing Phase 2A input/acknowledgement contract and receipt versions are preserved. Actor/org/operation/key binding, canonical payload fingerprints, current authorization before replay, digest/binding checks, original response and same-session domain/audit/receipt writes remain. Publish replay rechecks current reviewer qualifications and independence; it returns the committed release acknowledgement without comparing mutable current draft bytes, so a later edit does not erase a valid command result. New publication always compares current exact content. Request IDs are correlation only. Lost delivery is modeled by discarding a committed internal result and retrying; there is no new HTTP endpoint.

Audit adds review submitted/assigned/decided/superseded and release published. Targets are stored review/release IDs resolved in the same session through explicit catalog ports; audit contains no feedback/content. No TTL/deletion/migration or operational retention policy. Model/store APIs prevent application mutation of evidence/releases but privileged database writers remain a production IAM concern.

## Boundaries and unresolved decisions

No production SSO/APIs, real users/roles, frontend, public catalog/enrollment/progress, assessment/certificate, prototype import, threshold, media, simulation, jobs, deployment or Phase 2C. Corporate approval still needed for required capacities/count, reviewer qualification/lifecycle, author/editor/publisher independence, review replacement/appeal, release withdrawal/corrections, retention/legal hold, scope sharing, source rights and technical sign-off. Development approval is workflow evidence only, not industrial proficiency or permission to deploy.
